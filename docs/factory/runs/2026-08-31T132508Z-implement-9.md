## Test 19, and a finding about the invariant it pins

The queue item calls test 19 "the valuable one": `src/mcp/server.ts` records a load-bearing
registration order in prose only — *"More specific templates are registered before the bare
item template"* — and reordering was supposed to let the bare template swallow
`workitem://{id}/tree`.

Measured, by reordering the registrations by hand and re-running: **it does not.** With the
SDK version in this lockfile, `{id}` does not match across a `/`, so
`workitem://<id>/tree?...` still resolves to the tree resource however the registrations are
ordered. The prose invariant is defensive, not load-bearing today.

Test 19 therefore pins both halves, and says so in a comment so nobody over-reads it:

- **the read**: the tree URI returns `{ items, escalations }`, not the bare template's
  `{ item, transcript }` — the assertion that matters today;
- **the order**: `resources/templates/list` enumerates templates in registration order, so
  the bare template being listed last is the code comment made executable. Verified to fail
  on reorder: `AssertionError: expected 0 to be greater than 1`.

Second finding, recorded not fixed (it would need `src/`): the tree template
`workitem://{id}/tree{?depth,attention_only}` only matches when **both** query variables are
present. `workitem://<id>/tree` and `workitem://<id>/tree?depth=1` both come back
`Resource not found`. An agent reading the altitude query must supply both. Worth an issue.
