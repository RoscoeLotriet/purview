# FQ-3 gate 4, revision 3 — slice 4 split into 4a and 4b

Interactive spec run. One gate, approved by a human in session on 2026-08-31.

## What this run decided, and what it deliberately did not re-open

Gates 1–3 were untouched. Product, architecture and design for these tests were approved on
2026-08-29 and the split changes decomposition only, so re-running them would have re-decided
settled questions at cost. The human chose **revision-in-place of FQ-3's gate 4** over a new
`docs/factory/specs/FQ-9/` folder, following the precedent set when slice 0 split at revision 2.

Approved: slice 4 becomes **4a (resources, tests 18–20)** and **4b (concurrent agents, tests
21–24)**, split along the file boundary, which is also the test-group boundary. No test moved
between slices and none was trimmed.

## The evidence the split was made on

Not an estimate. Implement run `2026-08-31T132508Z-implement-9` wrote all seven tests, went
green at `full` gates, measured **488 lines against Charter §7's 400-line ceiling**, and
stopped.

| Slice | Estimated | Measured | Variance |
|---|---|---|---|
| 4 (before the split) | ~250 | 488 | **+95%** |

That is the fourth consecutive over-run and the worst in FQ-3. At ~70 measured lines per test,
no slice above five tests fits under the ceiling — recorded in both the spec and the status
file so the next sizing starts from the rate rather than from a fresh guess.

## The mechanism change, which matters more than the split

`00-status.md` predicted this split before the run and asked for the seam to be agreed in
advance. **The prediction was right and it did not help.** It lived in the spec and in the
status snapshot; it never reached #9's `factory-handoff:v1` comment, which is what the contract
makes authoritative and what an implement run actually reads. So a whole run's work was written
before the ceiling stopped it.

Revision 3 adds the rule: where a slice is suspected of exceeding the ceiling, the named seam
goes **in the handoff comment**, with the instruction to split at it without a spec run. That is
the difference between slice 2 (split cheaply, no spec run) and slices 3 and 4 (each stopped a
run and needed a human).

## A spec premise that turned out to be false

Revision 2 called test 19 "the valuable one" on the premise that reordering the resource
registrations would let the bare `workitem://{id}` template swallow `workitem://{id}/tree`. The
implement run reordered them by hand and re-ran: **it does not.** With the SDK version in this
lockfile `{id}` does not match across a `/`.

The `done_when` clause survives because the test reaches the invariant another way —
`resources/templates/list` enumerates templates in registration order, verified to fail on a
hand-reorder. Recorded in the spec, in #38's handoff, and in a comment in the test itself, so a
later reader meets the correction where it matters rather than trusting the prose.
