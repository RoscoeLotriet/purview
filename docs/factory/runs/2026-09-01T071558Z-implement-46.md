## Why the run stopped

`factory-implement` requires the run to check the item against `LOAD_BEARING` itself rather
than trusting triage. #46's entire implementation surface is `.claude/scripts/gates.sh`. Three
independent sources agree that this is out of bounds for an unattended run:

| Source | What it says |
|---|---|
| Charter §2 | `LOAD_BEARING` lists `.claude/**`. A change touching it is forced to a human read and may never be modified unattended, regardless of tier. |
| `CONTRACT.md` rule 2 | Never modify anything under `.claude/` unless a human explicitly asks **in the current session**. |
| The item's own handoff | `load_bearing: true`, and in prose: "This run will stop and need the human." |

The harness agrees mechanically as well: `.claude/settings.json` carries
`Edit(.claude/scripts/gates.sh)` in its `deny` list, so the edit would have been refused even
if policy had allowed it.

This is a scheduled run with no human in session. The contract's exception is explicit that
the request must come from a human in the current session, and a stored prompt firing on a
timer is not that. There is no reading of the contract under which this run could have made
the edit.

The skill's instruction for this case is `proceed not at all` — not proceed carefully — so the
run did not claim `claude/fq-46`, did not create the two new test files (which are themselves
outside the load-bearing set), and did not run gates. Landing the harness and tests alone would
have produced a green PR that satisfies none of `done_when`, because every clause of
`done_when` asserts on output the unwritten `gates.sh` changes are supposed to produce.
