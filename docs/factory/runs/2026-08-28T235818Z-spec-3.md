# Spec run — FQ-3, integration suite for the step-1 seams

## What was decided at each gate

**Gate 1 — product.** Approved with all six gaps in scope, against the recommendation to cut
two. The human's stated basis: step 1's code survives regardless of what the readout says, so
the resource surface and the restart boundary are worth pinning now.

The gate's substantive finding: product spec §8 says to read fan-out ratio and escalation
latency and stop before building steps 2–4, and §7 says immediate-band latency above ~10
minutes reads as "routing isn't working." A misconfigured Slack connection produces exactly
that signature — escalations raised, none seen, all timing out. A plumbing fault and a dead
product premise are indistinguishable on the dashboard the decision is made from.

The kill question was argued rather than skipped. The case against ("don't test a disposable
probe") was judged wrong on its main point but right about scope; the scope ranking it
produced was overridden by the human on the durability grounds above.

**Gate 2 — architecture.** Approved as written.

Decisive finding: there is no CI in this repository, and the gates script's test gate invokes
exactly `pnpm test`. The conventional split — integration behind its own script — would have
produced a suite that runs in no gate at all. So `pnpm test` runs both projects and
`pnpm test:unit` is the fast loop. The default is the complete one.

Also settled: zero new dependencies (interceptor libraries rejected because gap 3 must prove
real outbound HTTP, not that an interceptor works); real timers throughout; and the flakiness
trap that `/slack/interactions` acks 200 before doing its work, so no assertion may be made
on that response.

No load-bearing path is involved, so the mandatory `factory-critic` pass for load-bearing
work was not triggered. Offered and declined.

**Gate 3 — design.** Approved. 25 tests, contracts for six harness modules, no
implementations.

Finding that narrowed a gate-1 claim: `PurviewService.notify` (`src/service/purview.ts:727-738`)
swallows every bridge failure by design. So the confound identified at gate 1 is structural,
not accidental — the suite can make it reproducible in a test but cannot make it observable at
runtime without a `src/` change. Gate 1's claim was corrected in place rather than left
standing, and the gap became follow-up issue #12.

Standing instruction recorded from this gate: seven tests spawn the real entrypoint as a child
process; if they need retries or sleeps beyond one `EADDRINUSE` retry, that is a verdict that
the entrypoint is not testable as written, and the response is to file the `src/`
config-extraction issue — not to add a retry.

**Gate 4 — slices.** Approved. Six slices plus two follow-ups.

The decomposition's load-bearing decision is a labelling one: every slice consumes slice 0's
harness, so labelling them all `ready-to-implement` would have had six runs each build an
incompatible harness. Only slice 0 is claimable; the rest are `wait-to-implement` with named
blockers.

## One process defect — first diagnosis was wrong, corrected here

Issue #3 briefly carried two `factory-handoff:v1` comments with conflicting dispositions —
the state the contract forbids. It was detected by re-reading the comment list, and the stale
copy was deleted.

**This run's first diagnosis blamed `gh issue comment --edit-last` for appending rather than
editing. That was wrong**, and is corrected here rather than left standing, because the
correct cause has a different lesson. Reconstructing from comment timestamps and the
concurrent triage run's own record:

| Time (UTC) | Event |
|---|---|
| 23:04:57 | This session's handoff comment on #3, `ready-to-spec` (id 5458671033) |
| 23:08:31 | `factory-triage` (#4) finishes its sweep over #3 |
| 23:09:00 | **Triage posts a second handoff comment**, `ready-to-spec` (id 5458698288) |
| 23:57:33 | This run's `--edit-last` edits the *most recent* comment — triage's — to `wait-to-implement` |
| 23:58 | This run deletes 5458671033, its own now-stale original |

So `--edit-last` behaved correctly. It edits the author's most recent comment, which was not
the one this session wrote. The duplicate was **created by triage**, which its own commit
message states plainly: *"posted an updated handoff comment since no comment-edit tool was
available to update the existing one in place."* The contract requires the opposite —
"Update the existing handoff comment when re-triaging instead of accumulating conflicting
copies."

Two real lessons, neither of which was the original one:

1. **`factory-triage` needs a comment-update path.** Lacking one, it will keep doubling
   handoff comments on every re-triage, and the next routine reads whichever it finds first.
   This is a factory defect, not a one-off.
2. **`--edit-last` is unsafe under concurrency.** With two routines writing to one issue,
   "last" is not "mine". Fetch the comment id and PATCH it explicitly, then verify.

## A second observation about the concurrent triage run

Triage's run record states that #3 "had zero labels despite the comment" and that it applied
`factory:ready-to-spec`. The issue was in fact created with that label already applied. The
likely explanation is benign — triage's sweep started at 23:04:00 and the issue was created
seconds later, so it may have queried a list that predated the label rather than misreported
it. Recorded here without a claim either way, because if it is instead a read-after-write
staleness in the triage query, it would make triage's counts unreliable in exactly the
situation the factory is built for: two routines working at once.

Not filed as an issue. One ambiguous timestamp is not evidence of a defect, and the next
triage run will show whether it recurs.
