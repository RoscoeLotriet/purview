## What changed

Two added files, three tests:

- **6** — the entrypoint serves `/healthz`, `/mcp` and `/slack/interactions` on `PORT`. The
  `/slack/interactions` assertion is on *mounting* (404 vs 200), which is the one thing that
  route's status code can prove, since it acks before doing any work.
- **9** — with `SLACK_WEBHOOK_URL` unset the process starts, logs the card via `[slack:off]`
  instead of posting it, nothing arrives at the fake, and a signed tap still releases a
  blocked agent. The escalation id comes off the item's transcript, because with no card
  there is nothing to read an `action_id` from.
- **11** — `SIGTERM` closes the listener and the process exits **0**, through the shutdown
  handler rather than by the default signal disposition.

`server-proc.ts` spawns the real entrypoint with `node --import tsx` — no shell, no guessing
at a path under `node_modules/.bin`, the same interpreter vitest runs under. `env` values of
`undefined` *unset* the variable, so an ambient `SLACK_SIGNING_SECRET` cannot silently turn
test 8 (in #26) into a different test. Children are tracked in a module-level set with a
`process.on('exit')` SIGKILL sweep, so a test that fails before teardown cannot leave a `tsx`
process holding a port.

## Two deviations from the `ServerProc` contract in 03-design.md

Named here because a reader of the design doc will otherwise find the contract silently
widened:

1. **`exitCode` added.** Test 11's claim is that the process *exits cleanly*, and `exitCode`
   is the only thing separating that from being killed by the default SIGTERM disposition or
   by this harness's own SIGKILL escape hatch. The verifier confirmed it is load-bearing:
   deleting `process.on('SIGTERM', shutdown)` fails the test on this assertion alone.
2. **`awaitStdout` added.** `startServerProc` resolves on the "listening" line, which is
   liveness, not the end of the startup banner. The first draft read the captured lines
   directly, passed three times standalone, and **failed under the full suite** — the
   configuration lines had not flushed yet. `awaitStdout` is the fix at the right layer.

A third addition, a public `stdout` array, was **removed** after verification flagged it as
unused: leaving it beside `awaitStdout` invites the next reader into exactly the race that
was just closed. `stderr` stays, as the design doc specifies.

## Gate 3's standing rule on retries

The rule: if these tests need retries or sleeps beyond a single `EADDRINUSE` retry to stay
green, the entrypoint is not testable as written and the run must stop and file the `src/`
config-extraction issue rather than paper over it.

Not triggered. The only accommodation touching the entrypoint's own timing is the one
`EADDRINUSE` retry the rule permits, and it is restricted to a port `startServerProc` chose
itself — a caller-pinned port that is taken is a real failure, which matters for slice 5,
which restarts on the same port deliberately. The two polling constructs (`awaitStdout`,
`awaitEscalationId`) wait on asynchronous conditions in the same shape as slice 0's
`SlackFake.awaitPost`; neither retries an operation that failed. The verifier was asked to
decide this independently and reached the same conclusion.

## Findings for the queue

**`PURVIEW_HUMAN` is not observable on any wire surface.** No MCP tool lists principals, and
`principal://{id}/queue` is keyed by id, so a principal's `display_name` never crosses the
wire. Worse, `src/http/app.ts` falls back to `service.defaultHuman` when it cannot match an
interaction's `user_name`, so a name-lookup assertion **cannot** distinguish a configured
human from `operator` — the obvious test for test 10 would pass against the bug it is meant
to catch. This was written into #26 so the next run does not have to rediscover it. Making it
observable is a `src/` change this slice may not make; whether it is worth doing is a
separate decision and no issue was filed for it.
