## A spec defect found while implementing the amendment

Gate 3 amendment 1 specifies `slack?: SlackFake` on `HarnessOptions`, "imported as a type
only, so `purview.ts` carries no runtime dependency on `slack-fake.ts` and slice 0a compiles
without it."

**That spelling does not typecheck.** A type-only import still requires the module to resolve,
and `slack-fake.ts` does not land until slice 0b.

Implemented instead as a structural interface declared in `purview.ts`:

```ts
export interface SlackTarget {
  readonly webhookUrl: string;
}
```

`webhookUrl` is the only member the harness uses. Slice 0b's `SlackFake` satisfies it by
shape, with no import in either direction. This reaches the amendment's stated goal exactly
while its literal text cannot. Recorded rather than silently substituted; a human should
confirm the amendment text is corrected before #18 is implemented against it.

## Why gates went red twice

Both failures were the same error, made twice: **asserting a data shape without reading it
first.**

**Red 1** — `types` and `test`. The test read `workitem://{id}` and asserted `stored.id`. That
resource returns `{ item, transcript }` (`src/mcp/server.ts:321-340`), so `stored.id` was
`undefined`. The type error was the same carelessness in another form: `contents[0].text`
without narrowing the text/blob union.

**Red 2** — `test` only. Types and lint fixed. The test then asserted
`stored.item.owner_id === 'scout'`. `claim` sets `owner_id = actor.id`
(`src/service/purview.ts:281`), and the `x-purview-principal` header is a *display name* —
`src/http/app.ts:30-32` passes it to `buildMcpServer`, which resolves a Principal with a
generated id. Received `pr_00daf456`. `owner_id` can never equal the header string.

The product code is not implicated in either failure. Both are defects in the new test.

## The fix, identified but deliberately not applied

The two-red rule is a circuit breaker on exactly this pattern, so the run stops here rather
than trying a third time.

The claim hop still needs proving — dropping the assertion would remove the only evidence that
the principal header reaches the service. The same resource payload already carries it: the
transcript holds a `state_change` entry whose message is `claimed by scout`, written from
`actor.display_name` (`src/service/purview.ts:285`). So:

- assert `owner_id` is a principal id (a non-empty string, `pr_`-prefixed), and
- assert the transcript contains the `claimed by scout` entry.

That proves header → principal → claim entirely on the wire surface. **One assertion pair in
one file. No harness change, no `src/` change.**
