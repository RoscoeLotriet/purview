## The finding, which is the reason this slice is 3a and not 3

Slice 3 was specced as tests 12–17, blocked on slice 0b alone. Tests 16 and 17 need a digest
to actually be **delivered**, and `PurviewService.flushDigest` has **no wire trigger**:

- none of the nine registered MCP tools reaches it;
- none of the three routes in `src/http/app.ts` reaches it;
- `harness/purview.ts` does not expose the `PurviewService` it constructs, and may not be
  modified under Charter §3;
- its only production caller is the `DIGEST_INTERVAL_MS` timer in `src/server.ts`.

So the only route to a flushed digest at integration altitude is the spawned entrypoint —
`harness/server-proc.ts`, which landed in slice 2a (#7) and was **not merged when this branch
was cut**. The spec never listed that dependency.

The run stopped at the boundary rather than improvising. The alternative available from `main`
at the time was to construct `PurviewService` and `SlackBridge` inline in the test file to
obtain a `flushDigest` handle. That was rejected on two grounds: it forks system construction
away from `harness/purview.ts`, and `02-architecture.md` forbids a test body calling a service
method directly. Both make it a scope decision, and an implement run does not own scope
decisions that were not pre-agreed — unlike slice 2, whose split point was agreed at gate 4.

Tests 16 and 17 are **#28**, with the trade-off written out so a human can overrule the choice
rather than discover it. #28 was filed blocked on #7; #7 has since merged, so it is unblocked
and left at `factory:wait-to-implement` for a triage run to promote.

Issue #8's `done_when` was edited **in place** from "tests 12-17" to "tests 12-15". The
verifier was right to insist: leaving it would have left an issue whose stated condition no
pull request against it could satisfy.

names #12 and says in terms that it is written to be flipped.
