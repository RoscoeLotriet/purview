## Nine days of unmerged triage PRs — the actual finding this run surfaces

This is not a queue-classification problem; it is an operational one, and it is the thing a
human reading this record most needs to see.

`main` is still at the commit the *previous* recorded triage run started from
(`docs/factory/QUEUE.md` on `main` predates #46–#51 even existing). Between then and now,
**nine consecutive daily `factory-triage` PRs (#52 through #60, 2026-09-01 through
2026-09-09) were opened and none has been merged.** This run opens a tenth. Each one
independently queried live GitHub state, found the same zero-change result documented above,
and each is titled `factory: triage <date>` — nine open PRs that, read together, say nothing
except "still nothing changed" nine times over.

This matters for three concrete reasons, not just tidiness:

1. **`docs/factory/QUEUE.md` on `main` is now ten days stale** relative to live labels. The
   contract is explicit that live labels are authoritative and an unmerged snapshot must
   never block a routine — and it hasn't blocked anything — but any human who reads
   `QUEUE.md` on `main` directly (rather than the tip of the newest triage branch) is reading
   a queue that is missing #23 and #46–#51 entirely and still lists #3 as open.
2. **The run-record trail is fragmenting.** Two events visible only in issue comments — an
   unattended implement run claiming and correctly bouncing off #46 on 2026-09-01, and a
   later pass relabeling #23/#46 to `wait-to-implement` on 2026-09-01/02 — wrote no run
   record under `docs/factory/runs/` on `main`, because whatever produced them never merged
   either. `CONTRACT.md`'s "Durable evidence" section is explicit that every run writes one
   file under `docs/factory/runs/`; nine days of unmerged branches means `main`'s copy of that
   evidence trail has a nine-day gap in it.
3. **It is exactly the kind of accumulation the charter's back-pressure valve exists to
   surface**, even though it does not technically trip Charter §7's letter. §7 counts issues
   labeled `factory:awaiting-review`, and none of these nine PRs carry that label or attach to
   a queue issue — they are triage's own output, not implementation work. But the spirit of
   "the constraint on this factory is how many decisions are pending a human's judgment at
   once" applies here just as much: nine redundant, unreviewed PRs are nine decisions
   (merge or don't) sitting untouched, and an unattended routine producing a tenth without
   saying so plainly would be the least useful thing this triage run could do.

**Not a charter gap in the classification sense** — nothing here changes any issue's
disposition — but flagged in "Charter gaps" below because the charter and contract are silent
on what a triage routine should do when its own prior output has piled up unmerged, and
"open an eleventh tomorrow" is not a good default.

## Charter gaps

- **No mechanism named for a triage routine whose own output has gone unmerged for multiple
  cycles.** `CONTRACT.md` says an unmerged `QUEUE.md` snapshot must never block a later
  routine from seeing labeled work, and it hasn't — every disposition above was re-derived
  from live labels, not from any snapshot. But neither the contract nor the `factory-triage`
  skill says what a routine should do differently on cycle nine of "nothing changed, opening
  another PR" versus cycle one. A candidate for a future `factory-tune` decision: after N
  consecutive no-op triage PRs, either stop opening a new one (and instead comment on the
  most recent open triage PR that it is still current), or escalate more loudly than a line
  in a run record. Left as a gap rather than decided here, since changing what triage does on
  its own initiative is itself a process change, not a triage classification.
- Everything else this run touched resolved cleanly against `CHARTER.md` §2, §4, §6 and §7
  without needing the default-deny clause. No new charter-coverage gap found among the 13
  issues themselves.
