## A tooling limitation, recorded rather than worked around silently

The contract and skill both say to *update* an issue's existing `factory-handoff:v1` comment
in place rather than accumulate conflicting copies, and prior comments on these issues (e.g.
#8's) show that pattern working — a single comment object edited multiple times. The GitHub
MCP tools available to this session (`issue_write`, `add_issue_comment`, and the PR-comment
tools) expose no comment-edit call; `add_issue_comment` only creates new comments or reacts to
existing ones. Rather than silently leaving stale handoff comments in place after a label
promotion, I posted one new comment per promoted issue (#9, #10, #28), each explicitly marked
`<!-- factory-handoff:v1 -->` and stating in its first line that it supersedes the prior
handoff comment, which is left in place as history. This is a workaround, not the documented
behaviour — a human reading one of these issues cold will see two comments carrying the same
marker and needs the "supersedes" line to know which is live. Worth fixing at the tool layer;
noted as a charter gap below since neither the contract nor the skill anticipates a harness
without comment-edit access.

## Charter gaps

- **No mechanism named for updating a `factory-handoff:v1` comment when the available tools
  cannot edit in place.** The contract (`CONTRACT.md`, "Live queue protocol") and the triage
  skill both say "update the existing handoff comment... instead of accumulating conflicting
  copies," which assumes edit access exists. This session's GitHub MCP toolset does not
  provide it. I worked around this by posting a clearly-marked superseding comment (see above)
  rather than guessing at an unsupported call, but the charter is silent on what the *correct*
  behaviour is when the tools don't match the assumption, and a future run with the same
  toolset will hit the same gap. Worth a decision: either accept superseding comments as
  normal, or fix the toolset.

  without needing the default-deny clause.
