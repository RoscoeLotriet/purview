# Verify run — PR #14, the FQ-3 spec

PR #14 is documents only: 8 files under `docs/factory/`, the output of a `factory-spec` run.
The session that wrote it also drove this verification, so the cold read was delegated to an
independent `factory-verifier` context per contract rule 5. That context was given the diff
and the repository, not this session's reasoning.

## What verification means for a documents-only diff

There is no implementation hunk and no test, so `prove-test.sh` does not apply and
"does the test fail without the fix" is `could-not-determine` rather than `yes`. Recording it
as anything else would be a false green.

The defect class that does apply: **a spec that asserts something false about the codebase
becomes a bad map that six implementation runs follow.** So the verifier's primary task was to
check the documents' factual claims against source, trusting nothing the documents said.

## D4 — the open item

Charter §7 lists "The change would exceed 400 changed lines" as a stop condition, unqualified
by change type. This PR is ~1110 lines. Two readings are available and the routine cannot
choose between them:

1. The ceiling is a reviewer-attention limit and applies to any diff, in which case this PR
   should have stopped and asked before being written at this size.
2. The ceiling is about code, where 400 lines of logic is a genuine review burden, and a
   1110-line specification — most of it prose a reviewer skims by section — is a different
   thing wearing the same units.

The spec itself invokes the same 400-line ceiling to size its slices, which makes the
inconsistency visible: it is either bound by the rule it applies to its own children, or the
rule needs the qualification written into the charter.

**This is a human decision.** An agent waiving a charter stop condition on its own initiative
is the failure mode the charter exists to prevent. Recorded here unresolved rather than
silently passed.
