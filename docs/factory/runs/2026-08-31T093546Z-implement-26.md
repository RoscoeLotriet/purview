## What changed

One added file, three tests, all driving the real entrypoint spawned as a child process.

- **7 — with `SLACK_SIGNING_SECRET` set, an unsigned interaction is rejected.** The 401 is
  asserted, and a note in the file says why that status is legitimate evidence here where the
  200 ack is not: on a signature failure the route returns 401 *instead of* acknowledging,
  and never reads the payload. But a route that answered 401 and applied the work anyway
  would pass on the status code alone, so the non-release is proved directly with
  `stillPending`. The test then taps the same bytes **signed** and watches the agent release.
  Without that second tap, a form this test had built wrong would also produce
  401-then-still-pending and the test would pass for the wrong reason.
- **8 — with `SLACK_SIGNING_SECRET` unset, an unsigned interaction resolves an escalation**,
  and the answer is credited to the accountable human who did not send it
  (`resolved_by_id === routed_to_id`). Marked in the file, above the test, as
  **characterization, not endorsement**, with the reason the behaviour is dangerous, the
  statement that this is not a claim it is correct, and the instruction that if the default
  is ever changed the test should be rewritten to the new behaviour rather than deleted.
- **10 — `PURVIEW_HUMAN` names the accountable human**, via the two-link chain the issue
  prescribes. See below; this is the test most likely to be written wrong.

`arrangeBlockedAgent` does the setup all three share — spawn, park an agent on a blocking
escalation, read the tap off the delivered card. Only `SLACK_SIGNING_SECRET` differs between
the tests, and an explicit `undefined` unsets it so an ambient value cannot quietly turn test
8 into a different test. The card comes from the fake Slack rather than the transcript, which
is why this file needs no equivalent of slice 2a's `awaitEscalationId` polling helper.

## Test 10 and the trap slice 2a found

The obvious test for test 10 — tap as `dana`, assert the answer is credited to `dana` —
**passes against the bug it exists to catch.** `src/http/app.ts` falls back to
`service.defaultHuman` when no human matches an interaction's `user_name`, so an entrypoint
that ignored `PURVIEW_HUMAN` entirely would still credit the tap correctly. Slice 2a wrote
this into #26 so this run would not have to rediscover it.

The teeth are in link 1: `await server.awaitStdout('accountable human  dana')`. The
entrypoint's startup banner prints `service.defaultHuman.display_name` — the *resolved
principal*, not an echo of the environment variable — and that is the only surface anywhere
on which a principal's display name is observable. Link 2, `routed_to_id === resolved_by_id`,
is the service → routing → resolution half of the chain the handoff prescribed; the file's
comment says plainly that it is the weaker of the two and why the name-lookup assertion was
not written. The configured name is deliberately `dana` and not `operator`, the entrypoint's
own fallback, or link 1 would pass against an ignored variable too.

Making a `display_name` observable on the wire would be a `src/` change and a product
decision. Not required here, and no issue was filed for it.
